# BankInvest — устройство и решения

Документ для того, кто будет проект сопровождать: что и почему сделано именно так.

## 1. Исходное состояние

Было одно приложение: WinForms (.NET 8) + SQL Server. Все запросы (44 вызова `Db.Table/Exec/Scalar`),
вся бизнес-логика (комиссия, лимиты, остатки, целевые доли) были зашиты в интерфейсные классы или
в хранимые процедуры SQL Server (`usp_BuyListing`, `usp_UpdatePrices`).

Такую систему нельзя «просто» сделать совместной: два независимых клиента (браузер и приложение),
пишущих в базу мимо друг друга, разъедутся в правилах и в правах доступа.

## 2. Целевая архитектура

```
клиенты (тонкие)  →  HTTP REST /api  →  сервер (логика)  →  Microsoft SQL Server (база BankInvest)
```

* **Правила остались в базе.** «Торговое ядро» — те же процедуры SQL Server, что были в исходной
  системе: `usp_BuyListing` (покупка по предложению в одной транзакции: блокировка
  `UPDLOCK, HOLDLOCK`, проверки `ERR_OWN/ERR_QTY/ERR_SELLERQTY`, перенос бумаг, две записи в
  `Transactions` с комиссией 0,5 %) и `usp_UpdatePrices` (почасовые точки истории цен, ограничение
  цены по номиналу и сегменту). Сервер их только вызывает — `EXEC usp_BuyListing …`,
  `EXEC usp_UpdatePrices` раз в минуту (раньше это делал таймер десктопа).
* **Сервер отвечает за запросы и проверки уровня API.** Портфель, целевые доли, отчёты, NPV/IRR/PI,
  права доступа (клиент видит только своё), поиск и фильтры — `server/src/logic.js`;
  подключение, пул, транзакции и параметризация — `server/src/db.js`.
* **Десктоп стал «тонким клиентом».** Интерфейс не менялся, но вместо `Db.*` (ADO.NET → SQL Server)
  теперь `Api.*` (HTTP → сервер). Файл `Api.cs` — единственная точка общения с сервером.
* **Веб-версия — второй клиент того же API.** Никакой отдельной логики: те же эндпоинты, те же тексты
  (словари `i18n.json` сгенерированы из `Localization.cs`), то же оформление.
* **Совместная работа** обеспечивается двумя механизмами:
  1. общая база (по определению одно состояние данных);
  2. server-sent events `/api/events`: сервер сообщает всем клиентам «изменились данные»
     (`changed`, с логином автора) и «обновились котировки» (`prices`). Клиенты перечитывают
     открытый раздел — без опроса по таймеру и без лишней нагрузки.

## 3. Почему такие технологии

| Решение | Причина |
|---|---|
| Node.js 18+ и пакет `mssql` (драйвер TDS) | официальный драйвер Microsoft, работает и из Windows (в том числе с Windows-аутентификацией), и из Linux/macOS; `npm install` ставит всё нужное |
| SQL Server как единственное хранилище | требование заказчика: данные должны быть в SQL Server, а не в файле. Плюс сохраняются исходные процедуры и схема, а база видна в SSMS вместе с изменениями из веба и десктопа |
| Параметризованные запросы (`sp_executesql`) | защита от SQL-инъекций; mssql передаёт параметры отдельно от текста запроса |
| `sql.options.useUTC = false` | `GETDATE()` в процедурах — локальное время сервера; сервер читает даты в том же часовом поясе, поэтому графики и отчёты совпадают по времени |
| Нормализация результатов (`Date` → строка, `BigInt` → число) | клиенты (десктоп на `System.Text.Json` и веб) получают ровно те же типы, что раньше: `"2026-11-23 18:09:18"`, числа — `number` |
| REST + JSON | одинаково просто вызывать из C# (`System.Net.Http` + `System.Text.Json`, без пакетов) и из браузера (`fetch`) |
| SSE вместо WebSocket | однонаправленные уведомления «данные изменились» — именно то, что нужно; в C# читается построчно, в браузере поддерживается `EventSource`; нет рукопожатий и библиотек |
| Веб-версия без сборки (один `app.js`, без React) | проект должен запускаться «как есть», без node_modules и билд-шага; при этом используется тот же CSS-дизайн, что в WinForms |
| Токены в таблице `Sessions` | простой серверный «выход» и проверка прав на каждом запросе; токен хранится в `%AppData%\BankInvest\token.txt` (десктоп) и `localStorage` (веб) |

## 4. Безопасность и что нужно доработать для продакшена

Сделано: пароли — SHA-256 (как было в исходном приложении; хеши из старой базы подходят без миграции,
потому что алгоритм и кодировка совпадают), проверка прав на сервере, журнал действий,
параметризованные SQL-запросы, серверные проверки всех бизнес-правил, отдельный SQL-логин с
минимальными правами (`db_datareader` / `db_datawriter`), пароль — только в переменных окружения.

Намеренно не делалось (учебный проект, но перечисляю честно):

1. **HTTPS** — ставить reverse proxy (nginx/Caddy/IIS), сервер слушать на 127.0.0.1.
2. **Пароли**: перейти на PBKDF2/Argon2 с солью + миграция старых хешей.
3. **Ограничение частоты входа** (защита от перебора) и блокировка после N неудач.
4. **Роли на запись**: сейчас любой сотрудник может менять портфель любого клиента — при необходимости
   добавить проверку владельца/подразделения.
5. **Срок жизни токена** (сейчас сессия живёт до выхода) и CSRF-защита, если появится cookie-аутентификация.
6. **Права SQL-логина**: серверу нужен `db_ddladmin` только для автосоздания схемы; на рабочей базе
   его лучше отозвать и выполнять `db/schema.sql` вручную.

## 5. Соответствие прежней логике

| Было (SQL Server) | Стало |
|---|---|
| `usp_BuyListing` | **та же процедура в базе**; `L.buy()` только проверяет «своё предложение» и вызывает `EXEC usp_BuyListing`, а результат (цена, комиссия, сумма) собирает для ответа клиенту |
| `usp_UpdatePrices` | **та же процедура в базе**; сервер вызывает её раз в минуту и рассылает событие `prices` клиентам |
| `SELECT ... FROM Portfolio` в `MainForm.LoadPortfolio` | `L.portfolio()` + `recalc()` на сервере |
| Расчёт NPV/IRR/PI/Payback в `LoadProjects` | `L.projectMetrics()` |
| Отчёт за 30 дней в `LoadReport` | `L.report()` |
| Проверки в `Trading.Sell` | `L.sell()` (свободный остаток, коридор цены) |
| `Db.Audit` | `db.audit()` (таблица `AuditLog`) + событие всем клиентам |

Формулы и константы сохранены: комиссия `0.005`, коридор цены `[0.3·P, 3·P]`, IRR — бисекция 200 шагов на
интервале `[-0.99, 10]`, PI по ставке проекта, окупаемость линейной интерполяцией.

## 6. Как это устроено внутри (SQL Server)

| Слой | Файл | Что делает |
|---|---|---|
| Схема и процедуры | `db/schema.sql` | таблицы, индексы, `CHECK`-и, `usp_BuyListing`, `usp_UpdatePrices`; идемпотентен |
| Демо-данные | `db/seed.sql` | клиенты, бумаги, портфели, сделки, предложения, история цен; повторный запуск не создаёт дублей |
| Подключение | `server/src/db.js` | конфиг из переменных окружения, пул (`mssql.ConnectionPool`), `tx()` на отдельном соединении, `OUTPUT INSERTED.Id` вместо `lastInsertRowid`, перевод ошибок SQL Server в понятные ключи `db.connect` / `db.login` / `db.permission` |
| Правила API | `server/src/logic.js` | асинхронные функции; даты и `BIGINT` нормализуются в строки и числа для клиентов |
| Точка входа | `server/src/server.js` | `await` в маршрутах, понятное сообщение при недоступной базе, `EXEC usp_UpdatePrices` раз в минуту, graceful shutdown (`SIGINT` → закрыть пул) |

Особенности, которые важно помнить при доработке:

1. **Диалект — T-SQL.** Вместо `LIMIT n` — `TOP (n)` или `OFFSET … FETCH NEXT`, вместо
   `datetime('now')` — `GETDATE()` / `SYSUTCDATETIME()`, вместо `IFNULL` — `ISNULL`,
   вместо `INSERT OR IGNORE` — `IF NOT EXISTS` / `MERGE`, вместо `strftime` — `CONVERT(CHAR(7), …)`.
   Зарезервированные имена — в квадратных скобках: `[Date]`, `[At]`.
2. **`TargetPct` в исходной схеме `NOT NULL DEFAULT 0`.** «Доля не задана» кодируется нулём;
   сумма целевых долей по-прежнему не может превышать 100 %.
3. **`Sessions`** — единственная добавленная таблица (токены входа сервера). В исходной базе её не было.
4. **Тесты** (`npm test`) работают на отдельной базе `BankInvestTest`, создают её перед прогоном и
   удаляют после — рабочая база не затрагивается. Если SQL Server недоступен, тесты помечаются
   `SKIP` с объяснением, а не падают.
5. **Драйвер асинхронный**, поэтому `await` обязателен во всей цепочке вызовов; синхронный стиль
   прежней SQLite-версии сюда не переносится.

## 7. Как расширять

* **Новый раздел**: эндпоинт в `server/src/server.js` → метод в `logic.js` → раздел в `app.js`
  (веб) и в `MainForm` (десктоп).
* **Новые тексты**: добавить пару в `Localization.cs`, затем `node tools/gen-i18n.js` —
  `server/src/i18n.json` обновится, веб-версия подхватит автоматически.
* **Новая таблица**: дописать `IF OBJECT_ID('X','U') IS NULL CREATE TABLE X(...)` в `db/schema.sql` —
  существующая база обновится при старте без потери данных (сервер выполняет файл, если каких-то
  объектов не хватает).
